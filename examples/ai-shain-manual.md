# AI社員の業務マニュアル（ひな形）

対象リポジトリの `.github/ai-shain.md` に置く。AI社員（担当・チェック担当）は、Issue を受けるたびにこの全文を読む。
長い決まりはここに写さず、どのファイルを読むかを書く。ここには「段取り」と「チェックの物差し」を書く。

## 最初に読むもの（この順に）

1. `CLAUDE.md`（決まり）
2. （世界観・文体・ブランドの文書があれば）
3. 同じ種類の見本ファイル（例：記事なら `src/articles/xxx.html`）
4. 進み具合（例：`status.md`）。同じ仕事を二重にしない

## 判断の物差し

この仕事は何のためにあるか（例：「トップ → 商品 → 最初の購入」）。迷ったら、どちらがこの流れを太くするかで決める。

## 仕事の種類ごとの進め方

### 記事・文章を書く／直す
- 見本をコピーして、front matter と本文を書き換える
- 出典のない数字・引用は書かない
- 最後に問いを一つ（手順の箇条書きで終わらない）
- `npm run build` → `npm test`。生成物も変更に含める

### 直す（崩れ・リンク切れ・設定・テスト）
- 再現 → 原因 → 最小の修正 → テスト

### 点検・チェック
- 対象のファイルを読み、問題を「場所・何が・どう直すか」の表にして PR 本文に書く。直せるものは直す

### 文書・決まりを書く
- 既存の文書の形に合わせる。日付と決めた人を書く

## やってはいけないこと（確認事項として PR 本文に書く）

- お金・販売・契約・個人情報・鍵・外部への投稿に関わる変更
- ページを消す・URL を変える
- git の commit / push

## 納品の形

- 変更したファイル、生成物、作業ログ（あれば）
- PR 本文：## 概要／## 変更内容／## 判断／## 確認したこと／## 残り・確認したいこと

## チェック担当の見るところ

- [ ] Issue との過不足
- [ ] 事実と出典（本文の番号と参考文献が一致、確かめられないものは削る）
- [ ] 言い方（禁じている言い回しがない）
- [ ] 決まり（ファイル名・登録・生成物・ログ）
- [ ] テスト・ビルドが通る
